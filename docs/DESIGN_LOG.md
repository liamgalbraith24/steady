# Steady — Design Log

A running record of what was built in each phase, the decisions made, the alternatives rejected, and open questions. This is raw material for `CASE_STUDY.md`.

---

## Phase 0 — Scaffold

**Built**
- TypeScript (strict) project that builds a Manifest V3 extension into `dist/` and the demo site into `dist-demo/`.
- `manifest.json` with a content script on `<all_urls>` at `document_idle` in all frames, an options page, a popup, and a `panic-toggle` command (`Ctrl+Shift+S`).
- A tiny MAIN-world script at `document_start` (used later for best-effort `dblclick` listener detection).
- Vitest unit tests, ESLint (flat config + typescript-eslint), Playwright e2e that loads the unpacked extension.
- GitHub Actions: `ci.yml` runs typecheck, lint, unit tests, build, and e2e. `pages.yml` publishes `dist-demo/` to GitHub Pages.
- Icons generated by `scripts/make-icons.mjs` (a hand-rolled PNG encoder, so no image dependency).

**Decisions**
- **esbuild build script instead of Vite + `@crxjs/vite-plugin`.** The spec allows "or equivalent". Every extension context here is a plain script with no HMR needs, and MV3 content scripts must be classic (non-module) scripts. `@crxjs` achieves that with a loader shim and a dynamic import, which adds a moving part to the one file that has to fail open. A 90-line `scripts/build.mjs` bundles each entry to a single IIFE, copies static files, and has a `--watch` mode. esbuild is also what Vite uses internally for TS transforms, so rebuilds are just as fast. Vitest still brings Vite in for tests.
- **Shadow-DOM overlay.** Steady draws its ghost cursor, rings, and drawers inside one closed shadow root on a fixed, `pointer-events: none` host. Page CSS cannot restyle it, and our CSS cannot leak into the page.
- **No offscreen document yet.** The offscreen document exists to own a webcam stream for head tracking (S2), because MV3 service workers have no DOM and content scripts should not hold long-lived media streams. S1 (switch scanning) was chosen as the stretch feature (see Phase 7), so the `offscreen` permission is **omitted** until S2 is built. Asking for unused permissions costs trust with users and at Web Store review.
- **Permissions: `storage` and `activeTab` only.** `scripting` (listed in the spec) was dropped because nothing needs programmatic injection. Already-open tabs pick Steady up when reloaded, and the popup says so. `activeTab` gives the popup the current tab's URL for the per-site toggle without the broad `tabs` permission.
- **Validation: `zod/mini`.** Zod v4's tree-shakable "mini" build keeps the content script small (the spec asks for zod validation at every message receipt).

**Dependencies added**
| Package | Why |
| --- | --- |
| `zod` (runtime) | Settings schema, migration, message validation. `zod/mini` keeps the bundle small. |
| `esbuild` | Bundler (see above). |
| `typescript`, `@types/chrome` | Types. |
| `vitest`, `jsdom` | Unit tests; jsdom for DOM-touching pure modules (scanner selectors, scan tree). |
| `eslint`, `@eslint/js`, `typescript-eslint`, `globals` | Lint. |
| `@playwright/test`, `axe-core` | e2e tests and accessibility scans. |

**Findings**
- Branded Google Chrome ≥ 137 ignores `--load-extension`. e2e tests use Playwright's Chromium on CI. On the Windows dev machine, Playwright's Chromium 153 zip would not start ("side-by-side configuration is incorrect"), so local runs point `STEADY_CHROME` at a Chrome for Testing binary instead (see `TESTING.md`).

**Open questions**
- None blocking.

## Phase 1 — Settings and profiles

**Built**
- `shared/settings.ts`: zod schema, defaults, `parseSettings` (strict, for imports), `migrate` (lenient, for storage), and export/import helpers. Three default profiles: *Steady (mild)*, *Steady (strong)*, and *Rest mode* (dwell on, strong filter).
- `shared/messages.ts`: a discriminated union for every cross-context message, validated at receipt with `parseMessage()`.
- Options page (plain HTML + TS): controls declare what they edit with `data-path` / `data-global`, and one generic binder keeps them in sync and autosaves (250 ms debounce) with a persistent, polite status line. There is a live before/after trace canvas using the real filter code, plus a **Play a sample movement** button, so keyboard and screen-reader users (and caregivers configuring remotely) can also see the effect. After movement settles, a summary is announced ("removed about 70% of the shake").
- Popup: profile switch, per-site toggle, panic button, study-log export/clear.
- Background: initialises/migrates settings on install and broadcasts `SETTINGS_UPDATED` to every tab when `chrome.storage.sync` changes. Panic state is per tab, stored in `chrome.storage.session` (the service worker can be killed at any time), and shown as an "OFF" badge.

**Decisions**
- **Two parsers.** Imports use `parseSettings`, which reports the first few issues in plain language and changes nothing on failure. Storage reads use `migrate`, which never throws: it upgrades v1, repairs partly valid profiles field by field, and otherwise falls back to defaults. A corrupt store must never stop Steady from failing open.
- **v1 → v2.** v1 is the prototype's flat single-profile shape. Migration turns it into a "My profile" profile (built from the mild or strong template) and keeps the three defaults alongside it.
- **One sync item.** All settings live under one `chrome.storage.sync` key. At about 700 B per profile the 8 KB per-item quota allows about 10 profiles, so the UI caps profiles at 10 and turns quota errors into a readable message. Splitting profiles across keys was rejected as needless complexity for now.
- **No native dialogs, nothing times out.** Delete, import and reset use inline confirm panels that move focus to the safe choice ("Keep it" / "Cancel"). Principle 2 (no time pressure) also rules out "Undo" toasts.
- **Inverted sliders where it helps.** "Steadiness" is a 1€ `minCutoff` where *lower* is steadier; the slider is inverted (`data-invert`) so right always means "more of the thing the label says".
- **Import is a button, not a styled `<label for=file>`.** Labels are not keyboard-focusable.
- **Demo bridge is origin-gated.** The demo page needs to talk to Steady (baseline condition, per-tab profile, simulated tremor, task markers). Letting *any* site detect Steady, or read profile names, would disclose that the user relies on assistive technology. So `content/bridge.ts` only answers on the demo's hosts (`shared/config.ts`), and everything it can do is tab-local and never persisted.
- **Per-site origin inside iframes** uses `location.ancestorOrigins`, so turning Steady off for a site also covers that site's embedded frames.

**Bug found in review:** `[hidden]` elements with `display: flex` classes stayed visible. Fixed with a global `[hidden] { display: none !important }`.

**Verified** (Playwright, `test/e2e/settings.spec.ts`): a settings change reaches a content script in another tab in about 100–300 ms (acceptance: < 1 s); malformed imports show an error and storage is byte-for-byte unchanged; axe-core reports 0 violations on the options page (including the switch section) and the popup.

**Open questions**
- Content bundle is about 36 KB minified, mostly zod's core. That is acceptable, but if it grows, message validation in the content script could move to hand-written guards.

## Phase 2 — Input pipeline and tremor filter

**Built**
- `InputSource` interface and `MouseSource`: trusted `pointermove` → samples, primary-button `pointerdown` → `activate` (carrying the native event), `Esc` → `cancel`. It also reports when the pointer leaves the document (for example into an iframe), so two ghosts never show at once.
- `OneEuroFilter` (Casiez et al., CHI 2012), with `ExponentialFilter` and `NoFilter` as baselines. `dt` is clamped to [1 ms, 100 ms] so a pause does not let one huge jump through unfiltered, and duplicate timestamps return the previous output.
- `Pipeline`: source → filter → overlay. Rendering is batched to one `requestAnimationFrame`. Every page-facing callback runs through `guard()`, so an exception tears Steady down on that page (principle 4).
- Shadow-DOM `Overlay` with a two-tone ghost cursor (black fill, white edge). It is also promoted to the top layer via `popover="manual"`, so it draws above modal `<dialog>`s and popovers.
- Hide-system-cursor option: a page-level `cursor: none !important` stylesheet, added only while the ghost is shown.
- Demo calibration section: live trace (using the active profile's real filter), per-tab profile picker, and a simulate-tremor slider.

**The ghost-cursor trade-off**
A content script cannot move the OS cursor. So Steady shows a *virtual* cursor at the filtered position and acts there: it highlights targets near the ghost, and (Phase 3) redirects clicks to them. The costs:
- Two cursors, unless the user hides the system one. Hiding it is the default in the *strong* and *Rest* profiles.
- CSS `:hover` still follows the real cursor. Only JS hover handlers can be driven synthetically (Phase 5).
- Native text selection and drag still use the real cursor. Out of scope; a note for future work.

**Simulated tremor (demo only)**
Two implementations, so each experimental condition gets the same stimulus:
- *Steady running:* the page asks Steady (bridge `SET_SIM_TREMOR`) to add the tremor **before** its filter, generated every animation frame from the last real position. Real tremor does not stop when the hand is still, so it must not depend on `pointermove`. The raw jittered point is drawn as a red dot next to the ghost.
- *Steady absent or paused (baseline):* the page draws its own jittering cursor and replays each click at the jittered point (`src/demo/pageTremor.ts`).

**Measured**
| Signal (unit test): 2 s sweep of 600 px + 5 Hz / 8 px sine, 120 Hz | HF energy kept | Lag at mid-sweep |
| --- | --- | --- |
| 1€ mild (minCutoff 1.0, β 0.005) | 28% | 7 px |
| 1€ strong (minCutoff 0.4, β 0.002) | 16% | 12 px |
| Exponential α = 0.08 | 11% | 29 px |

The exponential filter can match the smoothing, but only at 2–4× the lag during deliberate movement, which users feel as "the cursor is swimming". That is the case for 1€ as the default.

e2e (`test/e2e/filter.spec.ts`), strong profile, 8 px simulated tremor, pointer held still: raw spread 6.6 px → ghost 1.1 px. Main-thread cost per sample: mean 0.006 ms, p95 ≤ 0.1 ms (headless Chrome clamps `performance.now()` to 0.1 ms); per rendered frame, p95 ≤ 0.1 ms. The budget is 1 ms.

**Decisions**
- Stats (`content/perf.ts`) are always collected (a ring buffer of 512 floats) and are readable on the demo page via the bridge (`GET_PERF`). Measuring in real use beats a one-off DevTools profile.
- A failure now sets a distinct `error` suspension reason, which the popup explains ("reload to try again"), instead of pretending the page paused Steady.
- Removed identifying `data-steady-*` attributes from the overlay host and cursor style. **Limitation:** any page can still detect *a* foreign overlay element through DOM observation. The bridge's origin gate prevents disclosure of profile names and trivial API-based detection, not DOM-level detection. Recorded honestly for the case study.
